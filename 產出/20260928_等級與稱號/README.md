「每日」以台灣日期（UTC+8）切。

### 「極小修改」判準

1. 把修改前、修改後的整頁內容各自接起來，去掉所有空白、標點與符號（Unicode 的 P、S 類，含全形逗號句號、引號、括號、驚嘆號、表情符號）
2. 兩邊去掉相同的開頭與相同的結尾，剩下比較長的那一段的字數，就是「改了幾個字」
3. **不到 10 個字＝極小修改，0 分**。只改標點、空白一律是 0 字；10～199 字 +20；200 字以上 +30
4. 同一人在同一頁連續編輯（中間沒有別人改、每次間隔 60 分鐘內）併成一次，以「第一次改之前 → 最後一次改完」的總改動算分，拆成很多小改動拿不到比較多分
5. 按「還原」本身不給分

第 2 步不做逐字比對（免費方案 CPU 上限 10ms，兩萬字逐字比對會超過），散在頭尾兩處的小修改會被算成中間整段，偏多不偏少。

### 「7 天內被還原」判準

編輯（或一輪連續編輯）最後一次改完後 7 天內，同一頁出現一筆修改，內容等於這次編輯之前的版本，或是還原到比這次編輯更早的版本，這筆編輯就不給分。7 天後才被還原，分數保留。

### 「檢舉成立」判準

- 收藏、品項、版本：管理員「維持鎖定」、或檢舉人數達門檻且沒被解鎖、或收藏被管理員下架。成立時間分別是裁決時間、第 N 位檢舉的時間、下架時間
- 留言：被檢舉自動隱藏且管理員沒恢復、或被管理員刪除
- 成立後 7 天內被申訴翻案（管理員解鎖、恢復留言），+10 作廢、改 −5；達門檻之後才跟上檢舉的人不加分，被翻案時一樣 −5

### 防刷分

- 內容被檢舉成立、被隱藏、被刪除：那筆分數作廢，已入帳的也扣回。取消讚、刪留言、成交作廢同樣扣回
- 每日上限以「全部事件」排名：被刪掉的那則仍佔名額，不會由超額的下一則遞補，扣回才扣得到
- 同兩個帳號之間：互讚（兩個方向合計）最多計 20 次、互留言合計最多 10 則、成交每人最多 2 筆有分
- 按讚者被停權，他給的讚不算對方的「收到讚」
- 帳號停權：總分顯示 0。事件保留，恢復後分數回來（見文末待決定第 1 題）

## 計分怎麼跑

- 每一筆加減分是 `score_events` 一列（事件表）。按讚、留言、發文、成交、檢舉在動作當下**不寫任何計分資料**，每日排程從原始資料表補出事件；只有「編輯頁面」與「補發行年」在動作當下記一筆（要算改了幾個字、記誰補的）
- 每天台灣凌晨 2 點跟清理過期紀錄同一個 Cron 跑一次彙總：補事件、重算每筆狀態（待入帳／已入帳／作廢＋原因）、加總到 `user_scores`、更新稱號 `user_titles`。全部是一次 D1 batch 裡的 SQL，Worker 端只組字串
- 管理員另有 `POST /api/admin/scores` 可手動重算（本機可帶 `now` 模擬未來時間，正式站不收這個參數）
- 個人頁顯示「分數統計於 2026-09-28 02:00（每天統計一次）」，本人另外看得到「另有 N 分待入帳」
- 三張新表都沒有內容版本觸發器。暱稱旁的等級在整頁快取的頁面（系列頁貢獻者、單則頁出價列表）最多跟著快取舊 5 分鐘；留言走 `/api/comments`、個人頁不快取，都是最新的

## 已知問題與取捨

1. 排程觸發本身沒在本機跑到：`wrangler dev --test-scheduled` 對這個預先打包的建置沒有作用（`/__scheduled` 404、`/cdn-cgi/handler/scheduled` 回 exception 且沒有任何 log）。排程呼叫的是跟管理員 API 同一支 `recomputeScores()`，函式本身驗過 126 項。上一輪的清理排程同樣只驗過函式。部署後隔天看 `counters.score_run_at` 有沒有更新，就知道排程有沒有跑
2. 每次統計都把全部事件重算一遍（讀取量跟事件數成正比）。D1 免費方案每天 500 萬列讀取，事件到幾十萬筆前不用擔心；再大就改成只重算最近 30 天的事件
3. 動作跟統計之間有延遲：今天按的讚明天凌晨才算進分數；取消讚若發生在統計之前，那個讚從頭到尾不算
4. 等級標籤在整頁快取的頁面最多舊 5 分鐘（快取 TTL）；不為了等級讓快取失效
5. 兩支舊腳本第一次沒全過，都是資料被驗收腳本自己弄髒，不是程式問題：
   - `上線後第一批`：它挑「最新一則有照片的收藏」測清快取、期望 2 個檔，挑到本輪驗收剛建、借用示範照片的收藏；它又數「強制顯示的藝人」期望 24，本輪驗收建的藝人設了強制顯示。本輪腳本改成借主圖縮圖分開的照片、藝人用自動顯示，本機既有的這批資料一併改掉後重跑 65/65
   - `其他系列與評論區`：它的 2h 期望「夜貓組只有一個系列」，但它自己第 3 段每跑一次就在夜貓組底下新建一個驗收系列，所以只有第一次跑會過。把前兩次驗收留下的兩個驗收系列隱藏後重跑 95/95（這支腳本本身不能重跑的問題沒改）
6. 補資料目前只有「系列發行年」一種。其他欄位（版本年份、目錄號待查證…）要不要也開放補、算分，待使用者決定
7. 管理員帳號照樣會產生事件、有分數，只是畫面一律顯示「館長」、不參加稱號
8. 總分是全部事件加總後才取 0：檢舉不成立的 −5 畫面上顯示 0，但會抵掉之後的加分（先 −5 再 +10＝5）
