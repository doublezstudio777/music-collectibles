## 必修清單

1. **`scripts/deploy.sh` 第 6 步煙霧測試會被 pipefail 誤判失敗，可能讓一次成功的部署被腳本回報成失敗**
   問題行：
   ```bash
   curl -fsS -D - -o /dev/null "$URL/" | grep -qi "^x-robots-tag: noindex" && echo "X-Robots-Tag noindex"
   curl -fsS "$URL/" | grep -q '<meta name="robots" content="noindex"' && echo "meta robots noindex"
   ```
   腳本開頭 `set -euo pipefail`。`grep -q` 找到第一個相符就關閉自己的 stdin，若 `curl` 這時還在寫（正式站首頁含 RSC 資料流，比本機測到的 101,735 bytes 大很多，且經 Cloudflare edge 分塊傳輸，比本機 loopback 更容易觸發），`curl` 會收到 SIGPIPE、回傳非零，`pipefail` 讓整條管線失敗，`set -e` 讓腳本在**部署其實已經成功**之後於煙霧測試這一步假性中止。
   證據：本機用同一支 `bash -c 'set -euo pipefail; ...'` 對 20 萬行資料流重現 SIGPIPE（exit 141）；對本機首頁（101,735 bytes，loopback）跑 15 次沒有重現，證明這是資料量／延遲相依、不是「本機測不出＝沒事」。這正是 `feedback_pipefail_grep_false_failure.md` 記錄的既有型態，只是這次出現在自家腳本裡。
   建議修法：先把回應存成暫存變數或檔案，`grep -q` 對已落地的資料做，不對管線做：
   ```bash
   BODY=$(curl -fsS "$URL/")
   grep -q '<meta name="robots" content="noindex"' <<<"$BODY" && echo "meta robots noindex"
   ```
   同段第 5 行 `curl -fsS -o /dev/null "$URL/"` 本身沒有管線，不受影響；`robots.txt` 檔案小，風險低但建議一併改掉求一致。
