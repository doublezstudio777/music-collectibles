### 連續瀏覽 100 次

10 個網址（首頁、`/artists`、4 位藝人頁、2 個系列頁、`/share/2`、`/login`）隨機，每次間隔 0.3 秒，不重試（`browse100.txt`）：

- **503：0 次**。200 共 94 次、404 共 6 次（`/share/2` 本來就是 404）
- 回應時間 p50 0.65 秒、p90 0.76 秒
- CPU p50 1ms、**p90 10ms**，超過 10ms 的 9 次。這 9 次裡 8 次是該網址在這個資料中心第一次被看（快取還沒有），另 1 次是第 87 筆的首頁（39ms），推測落到別的資料中心或快取被清掉，沒有查證

p90 剛好壓在 10ms，是因為 100 次裡有 10 個網址各要冷啟一次。網址一多、或內容剛改完，第一次看的那一下仍會超過 10ms（見「還沒解決的」）。

## 熱點

1. **每一頁都重新整頁渲染**。React 伺服器渲染本身就要 10～50ms，連完全不讀資料的 `/login` 也要 9ms。這是主因
2. **站內換頁的預先載入放大請求數**。瀏覽器每開一頁會對畫面上的連結發 RSC 預先載入請求，每個都是一次完整渲染，一個人瀏覽等於一次打十幾頁。本機實測一輪換頁就有 20 幾個 RSC 請求
3. **藝人可見性判斷是平方級**。`artistVisible` 對每位藝人跑 `sharesWithTag`，每則收藏的每個標籤又掃一遍整張藝人表。正式站還沒有收藏所以看不出來；本機有 108 則收藏，首頁與 `/artists` 一次要 **700ms**
4. 每個請求重讀整包內容目錄（11 張表）、解析 intro、awards 等 JSON。本機約 5ms

## 修法

### 整頁快取（`網站/worker.ts`，新的 Worker 進入點，包在 vinext 外面）

- 對象：GET 的首頁、`/artists`、`/artist/...`（含系列、歷史）、`/share/{數字}`、`/tag/...`、`/login`，回應 200 或 404、沒有 Set-Cookie、HTML 或 RSC
- 用 Cache API（`caches.default`）存 5 分鐘。存的時候把 Cache-Control 改成可快取、原值另存，送出時還原，所以瀏覽器端仍是原本的 `no-store`
- **快取鍵含內容版本號**。新表 `content_version`（一列），資料庫觸發器（57 個，19 張表 × 新增／修改／刪除）在公開頁面會讀到的表一有寫入就把版本加 1。每個請求先查這個版本號（一個很小的 D1 查詢）再查快取，跟上一輪 `/img/` 一樣是「先問 D1」，不靠清快取，所以隱藏、下架在每個資料中心都立刻生效。觸發器在資料庫層，程式忘了加、或直接下 SQL 也一樣會失效
- 快取鍵也含部署版本（`version_metadata` 綁定）與 RSC 相關標頭：新部署不會拿到舊 HTML；站內換頁的 RSC 請求跟整頁 HTML 分開存
- 觸發器涵蓋：artists、series、items、versions、version_marks、version_fakes、shares、photos、users、likes、holdings、reports、target_decisions、settings、revisions、deals、offers、artist_redirects、page_locks。不含私訊、session、驗證碼、計數器這類不影響公開頁面、又寫得很頻繁的表

### 頁面不再因人而異

整頁能共用的前提是登入者拿到的 HTML 跟訪客一樣：

- 讚數、我有／想要人數改成資料庫總數（含登入者自己）。原本是「扣掉自己那一下」，每個人看到的 HTML 都不一樣
- 前端新增 `lib/counts.ts` 的 `useLiveCount`：記下「拿到這份總數時自己按了沒」，扣回去再疊上現在的狀態，按了馬上變；換帳號或伺服器給了新總數就重記。登入者自己的狀態仍由原本的 `/api/me` 小請求取得
- `pageData()` 不再讀登入者（公開頁面本來就沒用到 viewer，只有後台用，後台改直接呼叫 `getViewer()`）
- 系列頁「最多讚」與首頁「最多讚」排序改用總數，跟 D1 算出來的順序一致；按讚後順序要重新整理才會換

### 內容目錄

- `lib/server/content.ts`：組好的目錄放在 Worker 記憶體，同一個版本號只組一次，最多用 5 分鐘
- `lib/catalog.ts`：藝人、收藏、系列改用查找表（第一次用到才建）；標籤鍵、每則收藏的標籤集合、「標籤 → 收藏」索引都記下來。本機首頁沒命中快取時從 713ms 降到 14ms

### 沒有做的

- 查詢只選需要的欄位、SQL 端過濾分頁：整頁快取加記憶體快取之後，讀目錄已經不是瓶頸（命中時完全不讀），改寫資料層的成本不值得，資料量再大一個級距再做
- 沒有加索引（沒有新增會用到索引的查詢）

## 還沒解決的

1. **沒命中快取的那一下仍會超過 10ms**（17～54ms）。發生在：內容剛改完（任何人按讚、發文、編輯都會讓全站快取作廢）、某網址在某個資料中心第一次被看、快取 5 分鐘到期。低流量時大多撐得過（這次 100 次 0 失敗），但如果有人連續按讚又同時很多人在看，全站會一起冷掉。要再降得從渲染本身下手（例如藝人頁 54ms 的來源），或讓按讚、我有不作廢整頁（讚數改由前端小請求取得）
2. 頁面上「3 小時前」這類相對時間最多舊 5 分鐘
3. `/api/shares/{n}`、`/api/threads/{id}` 回傳的讚數也改成總數，前端一律經過 `useLiveCount`，目前沒有其他地方直接顯示這個數字
4. 這輪本機回歸重跑時，驗收腳本會覆寫上一輪 `產出/20260928_上線後第一批/img/` 的 7 張截圖；我已經把那 7 張還原成上一輪的版本，這輪重跑產生的新截圖在還原時一起被丟掉了，要看可以重跑腳本
