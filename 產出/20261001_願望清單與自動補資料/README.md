## 2. 連結預抓

升級 Workers Paid 後重新評估，**定案：滑鼠移到連結上才抓（intent）**，`components/link.tsx` 的 `MODE`。

| 本機建置版，iPhone 視窗，8 頁各開一次＋慢慢捲到底＋停 6 秒 | 打到 Worker 的請求 | 其中 RSC 預抓 |
|---|---|---|
| 不預抓（原本） | 25 | 0 |
| vinext 預設：進畫面就抓 | 297 | **272**（首頁 28、藝人 17、系列 16、收藏頁 15、私訊 11、願望清單 17、設定 14、**全部藝人 154**） |
| 滑鼠移上去才抓（採用） | 25 | 0 |

- 進畫面就抓：每開一頁多 11～154 個整頁渲染。用現在每月約 40 萬次請求粗估，會變成 300 萬次上下，仍在 1000 萬次額度內，但 CPU 會多出一大截（沒命中快取的頁一次 20～190ms），而且 `/artists` 一頁就 154 個，**不採用**
- 滑鼠移上去才抓：用 `router.prefetch(href, { kind: "full" })` 整頁抓好放進換頁快取，點下去 **0 個新請求**、本機換頁 45ms（不預抓是 84ms 並多打一次）。只在滑鼠移上去才抓，沒點的那幾次才是多出來的請求
- 手機不掛 touchstart：手機滑動時手指常按在卡片上，掛了等於一路滑一路抓。手機點擊時瀏覽器補發的 mouseenter 還是會先抓，抓的那一次就是換頁用的那一次，量測點擊流程（首頁→收藏→系列→藝人→願望清單）每步請求數跟不預抓相同
- 個別連結明寫 `prefetch` 可以蓋過全站預設

量測腳本 `_量測_預抓.py`，結果 `量測_預抓_{off,viewport,intent}.json`（intent 那份是還掛 touchstart 時量的，點擊流程結果相同）。

## 3. 每月補新作品（自動補資料第 2 層）

`lib/server/release-scan.ts`。每天 02:00 的排程看這個月開過沒，沒有就開一輪；實際查詢由 `*/10` 的排程在自動補資料沒工作時分批跑，**共用同一把鎖與 MusicBrainz 每秒 1 次的計時**，每次最多 45 次對外連線、2 分鐘。狀態存 `autofill_state` 的 `release_scan`，沒有新表。

對象：站上有 MBID 的藝人（正式站 146 位）。用藝人 MBID 列 release-group（專輯／EP／單曲），找「站上沒有同 MBID 的系列（含已刪除的，刪過的不補回來）、第一次發行在 365 天內」的。

**方案（照自動補資料的信心分級）**
- 高信心：藝人用 MBID 查（作品一定是這位的）＋站上沒有＋這位藝人底下沒有同名系列＋有實體正式發行 → **直接建系列並上站**，進後台「待確認的新增」（新增者寫「每月自動補新作品」），版本交給自動補資料建（資料狀態待確認、帶曲目）
- 疑義：這位藝人已經有同名（或互相包含）但沒有 MBID 的系列 → 不建，列在後台「每月補新作品」疑義清單
- 略過：只有數位、非正式發行、類型不是專輯／EP／單曲、超過一年。只有數位的一年內每月再看一次
- ⚠️ 跟 9/30 決策記錄「查到的先進後台『待確認的新增』由管理員確認才上站（使用者原話：「先進後台」）」不同：這次派工寫「預設照 autofill 的信心分級」，所以高信心是先上站、事後確認。要改回「確認才上站」見最後待決

後台 `/admin/additions` 最上面一塊：進度、統計、建了哪些、疑義、只有數位清單，「現在跑一輪」「接著查一批」。API `/api/admin/release-scan`。

**手動觸發結果**
