# 炫收藏表單藝人預設清單＋疑似重複藝人（2026-09-28）

用戶在正式站看到問題直接要求修改：表單一打開就把 233 位藝人全部列成按鈕，金曲金音名單裡的「凹與山」
「凹與山Our Shame」這類藝人排在匯入順序前面就自動跳出來，顏社的國蛋、蛋堡反而要往下滑才找得到。
原話：「幫我把上傳的內容 不要 凹與山 然後要放顏社的人員進去 國蛋 蛋堡 等」「不要凹與山是凹與山不要
讓他自然跳出來」。中途兩次追加指示：先把「最多顯示幾位」從「顏社＋本色全部」改成「最多 10 位＋更多
按鈕」；後來把「重複藝人清單寫進報告」改成「在後台做一頁讓用戶自己操作合併」。

## 一、預設清單怎麼決定

`網站/lib/catalog.ts` 的 `formOptions()`：

1. **強制顯示池**（`formArtistPool()`）＝全站最近有人發過收藏的藝人（新到舊，去重）接上
   `網站/lib/label-artists.ts` 的顏社（16 位）、本色音樂（8 位）固定名單（現任在前、前藝人在後），
   兩邊去重。這份池子之外的藝人（其餘 200 多位）表單完全不列按鈕，只能靠打字搜尋找到。
2. **預設十位**＝這位會員自己最近分享時選過的藝人（最多 5 位，排最前面）接上池子其餘部分，
   取前 10 位。沒登入時就是池子前 10 位。第 11 位開始收進「更多」按鈕，按下去才展開。
3. 男歌手／女歌手／團體 × 國內／國外那組分類按鈕，只篩選「目前列出的」（沒按更多就是預設 10 位，
   按過更多就是整個池子），不會篩到池子外的 200 多位。分類區底下固定一行「找不到？打字搜尋全部
   藝人」引導去用搜尋框。
4. 已經發過收藏的藝人（不管是不是顏社／本色）本來就在池子裡（第 1 點），所以之後有人發了某位藝人，
   他就會自然出現在預設清單，不用手動維護。

顏社／本色音樂名單來源：`研究/20260927_顏社本色音樂/藝人.csv`，硬寫進 `lib/label-artists.ts`
（不從資料庫欄位推導，因為 `tagline`／`source` 之後可能被人手動改動；這份名單本身異動很少）。

## 二、payload 變小

`formOptions()` 不再送出全部藝人，只送「預設 10 位＋更多池子」（實測本機約十幾到幾十位，遠小於
匯入的 233／本機示範 303 位）。打字搜尋改走新 API `GET /api/artists/search?q=`（查全部藝人，含
還沒出現在池子裡的），跟藝人目錄用的 `GET /api/artists`（只回前台看得到的）分開，因為表單要能選到
還沒有人分享過的藝人。

`components/share-form.tsx`：拿掉舊的 `ARTIST_CAP=30` 一次全塞的作法，改成 `defaultArtists`／
`moreArtists`／打字搜尋（debounce 300ms）三段拼起來的 `known` 清單，解析輸入、拼系列選項都吃這份。

## 三、疑似重複藝人（後台頁面，不是報告清單）

用戶中途改主意：一開始要「把重複藝人列成清單寫進報告」，後來改成「做一個後台頁面讓我自己操作」。
最終做法：

- **偵測規則**（`網站/lib/server/duplicates.ts`）：中文名完全相同／一方名稱是另一方前綴或後綴
  （例：「凹與山」和「凹與山Our Shame」、「青虫」和「青虫aoi」）／英文別名重疊／一方英文別名等於
  對方中文名。純用記憶體裡的目錄比對，跟表單搜尋同一份資料，藝人幾百位還在毫秒等級。
- **位置**：`/admin/duplicates`（管理後台新分頁），儀表板「待處理」多一格「疑似重複藝人」顯示組數。
- **三種操作**：
  1. **合併**：選保留哪一位，先「預覽合併」看會搬動幾筆（系列、炫收藏、我有／想要、成交紀錄、追蹤、
     不感興趣、編輯紀錄、裁決、頁面鎖定），才能「確認合併」。系列會重新編號搬到保留者底下（流水號是
     「藝人底下」流水號，不能跟保留者已用過的號碰撞），所有引用到那個系列鍵的地方跟著換新鍵；被合併
     那位的名稱＋別名併進保留者的別名（之後舊收藏文字裡寫的那個名字還是找得到人）、得獎紀錄併過去、
     識別碼寫進 `artist_redirects`（跟改識別碼共用同一張表，連續合併／改名都只轉一次），舊網址 301。
     被合併那位軟刪除（`deleted_at`），不會再出現在目錄、表單、搜尋裡。全部在同一個 D1 batch（同一個
     交易）做完，中途失敗整批不生效。
  2. **不是重複**：寫一筆 `artist_duplicate_marks`，這組之後不再列出。
  3. **稍後處理**：不寫資料庫，只是這次先跳過，下次重新整理還會再出現。
- **遷移**：`drizzle/0010_artist_duplicates.sql`，只新增 `artist_duplicate_marks` 一張表，沒有動
  既有表與欄位。

**正式站沒有幫用戶合併任何一組**，只部署功能本身，讓用戶自己在後台操作。

## 四、跑舊驗收時抓到一個真的競態問題（已修）

重跑 `等級與稱號/_驗收_本機.py` 時 15h 步驟卡住：打字打完整名字、點下拉建議、選系列時「這裡沒有，
我要新增」按鈕一直等不到。原因：打字搜尋改走 API 後有 300ms debounce，如果打完整名字後**在搜尋回來
前**就點下拉選項，這時候畫面上「打字當標籤」的回退按鈕跟「真的那位藝人」的建議按鈕文字長得一模一樣
（因為搜尋還沒回來，程式還不知道這位藝人存在），Playwright（跟手快的真人）會點到回退按鈕，選到的
是純文字標籤，不是真的那位藝人；且選定當下會清空輸入框，把還在飛行中的搜尋請求整個取消掉，之後也不
會自己補回來。

修法（`components/share-form.tsx`）：多一個 `searchedQuery` 記錄「最後一次真的查完的字」，回退的
「當標籤」選項只在確認搜尋已經查過這個字、而且真的沒有這位藝人時才出現；點下拉建議時直接把整個藝人
物件塞進 `found`，不用等下一輪搜尋回來才解析，徹底不看網路請求的時間點。修完後 165/165、25/25 都過。
