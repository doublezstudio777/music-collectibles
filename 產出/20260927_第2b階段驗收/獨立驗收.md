### 上傳：偽造 Content-Type／副檔名

| 測試 | 結果 |
|---|---|
| HTML 內容（`<html><script>alert(1)</script></html>`）改檔名 `evil.jpg`、Content-Type `image/jpeg` | ✅ 415 BAD_FORMAT |
| SVG 內容（含 `<script>`）改檔名 `evil2.jpg`、Content-Type `image/jpeg` | ✅ 415 BAD_FORMAT |
| 真 PNG 檔案改檔名 `real.jpg`、Content-Type `image/jpeg` | ✅ 415 BAD_FORMAT（看檔頭 magic bytes，不採信副檔名或瀏覽器宣稱的 Content-Type） |
| 第 31 張上傳（同一天） | ✅ 429 DAILY_LIMIT，第 30 張以內全部 201 |
| `/img/{key}` 回應 Content-Type | ✅ 正確（`image/webp`） |
| `/img/{key}` 回應 `X-Content-Type-Options` | ❌ **沒有這個標頭**（`curl -I` 確認缺失） |

**評估**：因為上傳時已用 magic bytes 嚴格檢查（`sniff()` 只認 WebP／JPEG 檔頭），偽裝成圖片的 HTML/SVG 進不了 R2，所以現況下無法透過這個路徑真的存進可執行內容——**缺 nosniff 標頭本身目前打不出實際攻擊**，屬於防禦縱深的缺口而非可利用漏洞。但這是一行程式碼的事（`"X-Content-Type-Options": "nosniff"`），沒有理由不補，日後若上傳驗證邏輯被改鬆，這行是最後一道防線。

**方法論修正記錄**：我第一輪腳本用預設檢舉門檻（10）送出 2 筆檢舉就期待觸發鎖定，結果「鎖定後出價/改價」兩項回 `{"ok": true}`——**看起來像是繞過了鎖定**。深查後發現：報告門檻本來就還沒到（2 < 10），系統壓根還沒進入鎖定狀態，這兩次操作本來就該成功，不是安全缺陷。改用管理員 API `POST /api/admin/threshold {value:2}` 先把門檻調到 2、確認 `settings.report_threshold` 真的變成 2 之後，用全新帳號重測：**出價回 423 LOCKED、改定價回 423 LOCKED**，鎖定判斷在 API 層確實生效，測完把門檻調回 10。這個坑值得記錄：**驗鎖定類功能前必須先用管理端點把門檻調到測試值，並且讀資料庫確認門檻真的變了，不能只送檢舉次數就直接下結論**。

### 私訊、炫收藏文字欄位 XSS

- 炫收藏 `story` 欄位塞 `驗收<script>window.__xss=1</script>` → 渲染後 `window.__xss !== 1`（腳本沒執行），且渲染出的 HTML 不含原始 `<script>` 標籤（React 預設跳脫）
- 私訊訊息塞 `<img src=x onerror=window.__msgxss=1>` → 同樣不執行、不原樣輸出
- 全庫掃過 `dangerouslySetInnerHTML`：只有 `components/ui/chart.tsx` 用來輸出**寫死的圖表色票 CSS**，不含任何使用者輸入，非風險點

### 忘記密碼頻率限制、回應一致性

- 同一 IP 每小時第 11 次起 429（`codes=[200]*10+[429,429]`）
- 已註冊 Email 與未註冊 Email 的回應**逐字元完全相同**（`{"ok":true}`，HTTP 200），不洩露帳號是否存在

### `/settings` 改密碼、刪除帳號

- A2 用瀏覽器 cookie session 登入後，改密碼（正確舊密碼）：**同一個瀏覽器 context 的舊 cookie session 立刻失效**（`fetch('/api/me')` 從 `user:{...}` 變成 `user:null`），符合「其他裝置全部登出」的設計
- 刪除帳號：申請成功後直接查 D1，`shares`／`photos` 筆數改動前後**完全相同**（`{'shares': 1, 'photos': 2}` → `{'shares': 1, 'photos': 2}`），`users.deletion_requested_at` 有值但 email／handle 都還在，帳號申請期間仍可正常打 `/api/me/state`。**PM「只做申請，沒有真的刪除任何資料」的描述屬實**
