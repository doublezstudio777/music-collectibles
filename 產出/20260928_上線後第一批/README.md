## 一、照片快取

### 成因

正式站已刪檔的 `/img/p/bME6O68hJ9GxBmf2.webp` 回 200、`cf-cache-status: HIT`、`age: 5401`。

- 開 `wrangler tail` 連打 3 次這個網址，3 次都有 Worker 執行紀錄（cpuTime 4～29ms）。CDN 層如果直接回應，Worker 不會被叫起來，所以 `HIT` 不是 CDN 層
- 同網址加 `?x=1` 回 404：舊程式快取鍵是完整網址，換查詢字串就沒中、去 R2 讀，檔案已刪所以 404
- 結論：`HIT` 是 `/img/` 路由自己用 `caches.default.put` 放進去的 Cache API 副本
- 部署新版後同一個網址立刻回 404、`Cache-Control: no-store`：如果是 CDN 層，新程式根本碰不到那份副本，會繼續 HIT。這也反向證實是 Worker 層

### 解法

1. `/img/` 先查 D1 再查快取。原本每次就要查暫停狀態與本月讀取數，照片查詢併在同一個 batch 並 JOIN 炫收藏：照片標刪除、資料庫沒有這張、收藏不存在／被隱藏／被刪除 → 404，順手把這個資料中心的快取副本丟掉
2. 管理員隱藏炫收藏時，`caches.default.delete` 清主圖與縮圖（API 回 `purgedPhotos`）
3. 快取鍵改成「來源＋路徑」，不含查詢字串

只清快取不夠：Cloudflare 文件寫明 `cache.delete` 只清當下那個資料中心，別的資料中心的副本清不到。第 1 項才是讓每個地方都立刻 404 的那一層。D1 請求數不變、R2 讀取不變。完整理由寫在 `產出/20260927_第2階段技術設計.md` 第二十三節。

## 已知問題與取捨

1. 🔴 匯入後藝人相關頁面間歇 503（exceededCpu），見最上面
2. 精選的「已確認版本」看的是版本本身的資料狀態：同一個版本區塊裡所有收藏掛的是同一個版本，所以版本是「待確認」時，勾了辨識參考的收藏不會被提前，只照讚數與時間排。照規格字面做，若要「待確認版本也讓辨識參考優先」要再說
3. 「在賣的」排除被檢舉鎖定的收藏，跟首頁「只看在賣」同一個判斷
4. 瀏覽器端快取沒改（`public, max-age=31536000, immutable`）：看過照片的人自己瀏覽器裡的副本清不到。改短會讓每次回訪多一次 Worker 請求，測試期不值得
5. `cache.delete` 只清當下的資料中心；其他資料中心的舊副本不主動清，但因為每次先查 D1，那些副本不會再被送出去，有人打到時也會順手丟掉
6. 被隱藏的收藏，管理員自己也看不到照片（`/img/` 一律 404），後台只有標題
7. 版本名稱是從「版本說明」自動取的：有標準版／豪華限定版／限定版／再版／USB 就用那個字，沒有就用「年份＋品項」（例「2010 CD」）；目錄號只從「catno」字樣取，「另有 2007 年版（catno …）」這種指的是別的版本，不取
8. `收斂水（再版）` 併進《收斂水》系列當第二個 CD 版本（2015 再版），沒有另開系列
9. DVD 與藍光併成同一個品項「藍光／DVD」底下兩個版本（跟站上既有品項類型一致）
10. 研究備註（例「Discogs列有兩個catno版本」「關係待確認（見README）」）原文放進系列正文，當作資料來源說明；系列正文是維基式可編輯的，之後有人補再改
