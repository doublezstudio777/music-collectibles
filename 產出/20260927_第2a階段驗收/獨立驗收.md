### 額外抓到的問題（原任務清單沒明列，但屬於「安全面實測」範疇）

1. **`forgot-password` 沒有 rate limit**（其餘 4 支 auth 端點都有）。雖然 `sendCode()` 本身有「60 秒內同一使用者不重寄」的冷卻，攻擊者仍可對**大量不同信箱**無限制呼叫這支（沒有 per-IP 或 per-email 的 `hit()` 檢查），可被當信件轟炸的放大器，或拿來測試 Turnstile 之外還有沒有別的節流。設計文件與 README 都沒提到這支要不要限流，屬於規格未講清楚，不算違反 2a 的既定驗收條件，但建議 2b／2c 補一個 `hit(`forgot:${ip}`, N, window)`。
2. **本機環境可偽造 `cf-connecting-ip` header 繞過所有 IP 級頻率限制**（register 的 per-IP 限制、resend-code 的 per-IP 限制）。實測：`curl -H "cf-connecting-ip: 10.0.0.99"` 直接跳過已經打滿的 `register:127.0.0.1` 額度，立刻又能再註冊。**這在正式 Cloudflare 環境下通常不成立**——Cloudflare edge 會覆寫用戶端送來的 `cf-connecting-ip`，客戶端無法偽造；但這代表整套 IP 級限流的正確性完全依賴「請求真的是由 Cloudflare edge 轉進來」這個假設，一旦部署設定有誤（例如源站被直接連到、或中間多一層代理沒有正確處理該表頭），限流會整層失效且沒有任何後備機制。屬於**部署前必須確認的假設**，不是 2a 程式邏輯的錯，但建議寫進 2c 部署檢查清單：「用非 Cloudflare 路徑直連源站，確認 `cf-connecting-ip` 不可被覆寫／該路徑本身不可達」。
3. **頭像選單「設定」連到 `/settings`，該路由回 404**（見矩陣第20項）。這是死連結，不影響 2a 的 API／帳號邏輯，但使用者點了會看到框架的英文 404 頁，體感很差。判斷這頁本來就不在 2a 範圍（帳號設定頁應該是後續階段），建議先把選單項目藏起來或標「即將推出」，不要留一個會 404 的連結。
