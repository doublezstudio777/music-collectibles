# 產品框架與網站開發方向討論

**日期**：2026-09-20

**參與者**：使用者、Codex

**用途**：保存今天的完整決策脈絡，供未來 Claude Code 與 Codex 接續，不只記錄最後結論。

## 一、今天從哪裡開始

使用者原先想開始開發台灣音樂收藏平台，先問應該做網站還是 App，以及是否需要先畫開發流程圖、拆清楚階段性任務。

討論後確認，真正要先處理的不是畫面數量，而是先建立一套可讓使用者理解與使用的資料框架：

1. **作品**：例如一張專輯或一個發行企劃。
2. **發行版本**：年份、地區、格式、品號、授權單位、包裝與內容物差異。
3. **個人收藏品**：某位使用者實際持有的那一件，以及保存狀況、照片、公開範圍與故事。

這三層不能混在一起。否則同一張專輯的不同版本會互相覆蓋，個人收藏狀況也會污染公共資料。

因此先完成第一版資料模型、20 件收藏測試表及分階段開發流程，再開始網站畫面。相關文件：

- `產出/20260920_版本資料模型與建檔框架.md`
- `產出/20260920_收藏版本建檔測試.xlsx`
- `產出/20260920_開發流程與階段任務.md`

## 二、網站還是 App

結論是先做**手機優先的響應式 Web App**，不先做原生 iOS／Android App。

理由：

- 目前需要驗證的是版本資料、收藏、分享與貢獻流程，瀏覽器已能完成。
- 網站可以用連結快速邀請收藏者，不必先安裝 App。
- 搜尋引擎能收錄公開版本頁，原生 App 做不到這一點。
- 帳號、資料庫與 API 若先設計好，未來仍可沿用到原生 App。
- 現階段沒有必須依賴推播、離線掃描或其他原生能力的高頻需求。

第一個畫面切片原本從「版本搜尋與收藏操作」開始，包含搜尋、格式篩選、版本詳細資料、「我有／想要」與候選版本入口。未做只有宣傳文字的形象首頁。

## 三、產品主體如何一路修正

### 第一個想法：版本目錄與收藏工具

最初網站以版本資料庫為主體，使用者主動搜尋，再標記自己擁有或想要的版本。這仍是平台不可缺少的基礎，但單獨放在首頁會偏工具感，對第一次進來的人不夠有吸引力。

### 第二個想法：預設推薦使用者可能喜歡的東西

使用者提出首頁應該主動推薦，而不是等人搜尋。這個方向成立，但「推薦商品」並不是最後答案。

第一版推薦原則：

- 使用已收藏版本、想要清單、關注音樂人、偏好格式與明確略過作為訊號。
- 每筆內容顯示推薦原因，先採可解釋規則，不先訓練推薦模型。
- 新使用者沒有行為資料時，先詢問少量偏好並混入編輯精選，不假裝已經理解他。
- 不以價格漲幅、高價稀有度或精確願望人數作為主要排序，避免把平台推向炒價。

### 第三個想法：主體應該是看別人的收藏分享

使用者進一步指出，更有趣的體驗應該是先主動邀請別人分享，而其他人的主要行為是觀看收藏分享。

這成為今天最重要的產品修正：

- **首頁主體**：收藏者的照片、故事、版本差異與尋物問題。
- **推薦對象**：分享、收藏者與故事，不只是商品。
- **資料庫角色**：支撐每篇分享，讓故事能連到正確作品與版本。
- **完整版本目錄**：保留為第二入口，供查詢與考據使用。
- **冷啟動方式**：主動邀請少量懂收藏的人，各分享一件有故事、難辨認或正在尋找的收藏；不要求他們先整理完整資料庫。

換句話說，資料庫是骨架，收藏分享是人會想看的內容。兩者不是二選一。

## 四、拍照、AI 與 MCP 的角色

使用者提出：收藏者能否拍照上傳，使用他自己的 AI 工具額度辨識物件、自動填寫資料，再寫進平台，降低建檔負擔。

這個方向被定義為**AI 輔助分享與建檔**，建議流程如下：

1. 收藏者拍攝封面、封底、條碼、目錄號、版權字樣及特殊內容物。
2. AI 從照片擷取候選欄位，並說明每個判斷的照片依據與信心程度。
3. AI 透過 MCP 搜尋平台既有版本，先嘗試配對，避免重複新增。
4. 找不到時，MCP 建立「待確認草稿」，而不是直接建立已確認版本。
5. 收藏者檢查、修正資料並補上一段故事。
6. 本人確認後才公開分享；若是新版本，另外進入候選版本審核流程。

### MCP 的定位

MCP 是 AI 與平台資料之間的橋樑，不是辨識模型本身。預計第一批工具為：

- 搜尋相似作品與版本。
- 建立待確認草稿。
- 更新草稿欄位與照片線索。
- 送出候選版本。

搜尋可以直接執行；建立、更新與送出等寫入動作必須經過使用者確認。

### 額度與費用不能先做的承諾

若使用者在支援圖片與 MCP 的 ChatGPT、Claude 或其他 AI 工具裡操作，可能由該工具理解照片，再呼叫平台 MCP。但圖片能力、MCP 支援與用量計算取決於各 AI 主機及使用者方案，平台不能宣稱一定使用使用者既有額度。

另一條路是讓照片直接上傳網站，由網站呼叫模型 API。這樣模型費用由平台負擔，也必須處理 API 金鑰、照片保存、刪除、隱私同意與失敗重試。第一階段暫不採用，但保留未來加入的可能。

### 安全與資料品質界線

- AI 結果永遠只是候選值，不能稱為真偽鑑定。
- 每個欄位保留照片依據、信心程度與使用者修正紀錄。
- AI 不可自動把草稿升級成已確認版本。
- AI 不可用時，使用者仍能用同一套一般表單完成建檔。
- AI 分析照片與公開展示照片要分開取得同意。
- 原始照片保存期限、EXIF 移除、刪除及通知下架流程仍需設計。

## 五、目前形成的產品循環

目前最一致的核心流程是：

**邀請收藏者 → 拍照 → AI 產生分享與版本草稿 → 本人補故事並確認 → 公開分享 → 其他人觀看、收藏或補線索 → 版本資料逐步完整**

這個循環同時解決兩個冷啟動問題：

- 平台需要有人願意看的內容。
- 版本資料庫需要有人願意貢獻資料。

收藏者不必為了「幫平台建資料庫」而工作；他是在分享自己的收藏，平台順便把可重用的版本資料整理出來。

## 七、刻意延後或否決的方向

- **不先做原生 App**：目前沒有網站無法滿足的必要需求。
- **不把首頁做成純商品推薦**：收藏者與故事比商品卡片更有觀看動機。
- **不先做交易金物流**：資料、收藏與局部供需尚未驗證。
- **不先做黑箱推薦模型**：初期資料不足，規則推薦較可控且能解釋。
- **不讓 AI 直接發布或認證版本**：錯誤會污染公共資料。
- **不從第一天由網站付費呼叫辨識 API**：會過早增加成本、照片隱私與營運責任。
- **不把目前虛構示範資料當正式種子資料**：真實 schema 必須先經過 20 件收藏測試。

## 八、接下來的合理順序

1. 用現有框架手工測試 20 件真實收藏，記錄辨認時間、缺少欄位與爭議。
2. 根據測試修正作品、版本、個人收藏品與分享的 schema。
3. 建立帳號、收藏狀態與一般「待確認草稿」API。
4. 完成一般候選版本表單、相似版本提醒與審核狀態。
5. 加入照片上傳、壓縮、權限、EXIF 移除、刪除與下架流程。
6. 將同一份草稿 API 開放為 MCP 工具，實測至少一個支援圖片的 AI 主機。
7. 邀請少量收藏者實際拍照分享，觀察是否真的比手動建檔方便。
8. 資料貢獻與回訪成立後，再評估交易與原生 App。

## 九、仍待決定與驗證

- 正式名稱是否沿用「留聲冊」。
- 第一批真實資料要限單一音樂人、10 組音樂人，或先限 CD／黑膠。
- 第一批測試者的登入與邀請方式。
- 收藏與分享的預設公開範圍。
- 什麼證據足以拆成不同版本；條碼相同但包裝或內容物不同時如何處理。
- 第一批要支援哪個 AI 主機。
- 各 AI 主機對圖片輸入、MCP 寫入、使用者確認與額度計算的實測結果。
- AI 草稿到底能把平均建檔時間降低多少，以及會增加多少人工修正與審核。

## 十、目前一句話產品方向

**讓台灣音樂收藏者用照片與故事分享自己的收藏，平台再把分享整理成可共同維護的作品與版本資料。**
